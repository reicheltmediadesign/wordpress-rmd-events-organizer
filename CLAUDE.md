# RMD Events Organizer – Projektregeln

WordPress-Plugin von reichelt media.design für Kunden-Websites, Ersatz für „Events Manager“. Repo: `github.com/reicheltmediadesign/wordpress-rmd-events-organizer`, Lizenz GPL-2.0-or-later, Autor Philipp Reichelt.

Events Manager dient nur als Orientierung: kein Code, keine Syntax, keine Platzhalter von dort übernehmen. Der vollständige Plan (inkl. Migration v0.2/v0.3 und späterer Buchung) liegt unter `C:\Users\phili\.claude\plans\sieh-dir-das-plugin-proud-wall.md`.

## Aufbau

- `rmd-events-organizer.php` Bootstrap (muss PHP-7-parsebar bleiben), `includes/` PSR-4 `RMD\EventsOrganizer\`.
- `includes/Domain/` ist **WordPress-frei** und wird mit plain PHPUnit getestet. `Domain\Validator` ist die einzige Instanz, die Datenformen definiert (Terminplan, Details, Adresse), `Domain\Settings` die der Einstellungen. Jeder Schreibpfad läuft dort durch.
- CPTs `rmd_eo_event` und `rmd_eo_location`, Taxonomien `rmd_eo_category` (Term-Meta `rmd_eo_color`) und `rmd_eo_tag`. Typ einer Veranstaltung (`event` | `market`) als Meta `_rmd_eo_kind`, Felder pro Typ in `Domain\Kinds`.
- **Terminplan** = Meta `_rmd_eo_schedule` (einzige Wahrheit): `entries` (`single` | `rule`, jede mit stabiler `id`), `exclusions`, `overrides`. `Domain\Schedule::expand()` erzeugt daraus Termine; `Domain\RecurrenceExpander` kennt nur Regeln und Daten (wird später für Terminbuchung wiederverwendet).
- **Tabelle `{prefix}rmd_eo_occurrences`** ist ein abgeleiteter Index (`Schema`). `Sync\OccurrenceSync` gleicht per `occ_key` ab (`<eintrag>` bzw. `<eintrag>:<Y-m-d>`), damit Zeilen-IDs stabil bleiben. Lokale Zeit ist die Wahrheit, UTC abgeleitet. Lesen ausschließlich über `Query\OccurrenceQuery`.
- **Module** (`Modules`): `locations`, `markets`, `calendar`, `migration`. Reihenfolge Default → Einstellung → Konstante `RMD_EO_MODULES` (sperrt den Schalter) → Filter `rmd_eo_modules`. Neue Module: Name in `Domain\Settings::MODULES` und `defaults()`, Konstante in `Modules`, Schalter in `Admin\SettingsPage`, Prüfung `Modules::is_on()` an den Einstiegspunkten.
- **Import aus Events Manager** (Modul `migration`, v0.2): `Migration\EmReader` ist die einzige Klasse, die die `em_*`-Tabellen liest (nur lesend; beide Schema-Generationen, vor 7.0 mit Regelspalten und ab 7.0 mit `event_type`/Regeltabelle, werden in dieselbe Form gebracht). `Migration\Planner` baut daraus Einheiten (eine Einheit = eine Veranstaltung hier), `Domain\Em\SeriesCollapser` fasst Serien zu Regel + Ausnahmen + Overrides zusammen und vergleicht das Ergebnis mit den vorhandenen Terminen (Paritätsprüfung, Abnahmekriterium: keine Abweichung). `Migration\Importer` schreibt idempotent über die Quell-IDs (`_rmd_eo_em_event_id`, `_rmd_eo_em_post_id`, `_rmd_eo_em_location_id`, Term-Meta `rmd_eo_em_term_id`) und kann alles Importierte wieder löschen. Gegen einen echten Kundenklon geprüft (EM 7.5, von älterer Version aktualisiert, 25 Einzelveranstaltungen, keine Serien): alle Veranstaltungen stimmen mit der Quelle überein. Dort auch gegen fünf von EM 7.5 selbst erzeugte Serien geprüft (wöchentlich, erster Samstag im Monat, zweiwöchentlich an zwei Tagen als Typ `recurring` ohne Beitrag je Termin, täglich, jährlich über zwei Tage; dazu ein gelöschter, ein verlegter, ein abgesagter und ein einzeln bearbeiteter Termin): keine Abweichung. EM 7.5 lässt beim Löschen eines Serientermins die Zeile mit Status 1 stehen und entfernt nur den Beitrag. Serien im alten Schema (5.x/6.x, Regelspalten) sind weiterhin nur über Unit-Tests der Regel-Abbildung geprüft.
- **Gleiche Adresse wie EM**: Solange EM aktiv ist und denselben Slug nutzt (`dbem_cp_events_slug`), weicht `PostTypes::event_slug()` auf `<slug>-2` aus, sonst liefern die EM-Einzelseiten 404 (auf einem Kundenklon passiert). `maybe_flush()` merkt sich die wirksamen Slugs und baut die Rewrite-Regeln neu, wenn EM an- oder abgeschaltet wird. Zeilen, deren Beitrag endgültig gelöscht wurde, importiert der `Planner` nicht (Zähler `deleted`).
- **Inhalte umstellen** (v0.3, Reiter 2 der Import-Seite): `Domain\Em\ShortcodeMapper` übersetzt einen EM-Shortcode in unseren (nur Bedeutung: Zeitraum, Anzahl, Filter; keine Formate), `Domain\Em\ContentConverter` wendet das auf einen Text an (Shortcodes, EM-Blöcke `events-manager/*`, die `CONTENTS`-Seiten) und meldet, was bleibt. Beide sind WordPress-frei und getestet. `Migration\Targets` löst alte IDs auf (Termin einer Serie → Serie), `ContentRewriter` (Beiträge, Original in Meta `_rmd_eo_em_content_backup`), `WidgetRewriter` (EM-Widgets → Block-Widgets, Option `rmd_eo_em_widget_backup`) und `MenuRewriter` (Meta `_rmd_eo_em_menu_backup`) schreiben und können zurücksetzen. `Importer::undo()` setzt diese drei zuerst zurück, weil WordPress Menüeinträge mit ihrem Ziel löscht.
- **EM-Reste entfernen** (Reiter 3): `Migration\Cleanup` ist die einzige Stelle, die fremde Daten löscht (feste Tabellenliste, `dbem_*`-Optionen, EM-Beitragstypen und -Taxonomien, Widgets, Capabilities, Cron). Nur bei inaktivem EM und mit eingetippter Bestätigung; nicht umkehrbar. Zum Testen vorher die Tabellen sichern.
- **CSV-Import** (`Events → CSV import`, immer vorhanden, Capability `rmd_eo_manage_events`): `Domain\Csv\CsvReader` liest die Datei (Trennzeichen `;`/`,`/Tab, UTF-8 oder Windows-1252, Spaltennamen englisch oder deutsch; die Spaltenliste `CsvReader::COLUMNS` ist die einzige Quelle für Vorlage, README und Admin-Tabelle), `Domain\Csv\CsvPlanner` macht aus den Zeilen Einheiten (eine Zeile = ein Termin, gleicher `key` = eine Veranstaltung, Stammdaten aus der ersten Zeile) und meldet unbrauchbare Zeilen mit Zeilennummer. Beide WordPress-frei und getestet. `Import\CsvImporter` schreibt; Wiedererkennung über Meta `_rmd_eo_csv_key`. Termin-IDs entstehen aus Datum + Beginn, damit ein erneuter Import die Termin-Zeilen (und von Hand abgesagte Termine) behält. Beim Aktualisieren ersetzt die Datei die Termine, alle anderen Werte nur, wenn sie in der Datei stehen. `Admin\CsvImportPage` hält die gelesene Datei bis zur Bestätigung in einem Transient je Benutzer. Keine Wiederholungsregeln in der CSV (bewusst).
- **Polylang** (`includes/Polylang.php`, tut ohne Polylang nichts): Veranstaltungen, Kategorien und Schlagwörter sind übersetzbar, Orte bewusst nicht. `OccurrenceQuery::find()` filtert auf die Sprache der Seite (Argument `lang`, nicht bei `event_id`); der Kalender gibt `lang` an den REST-Endpunkt weiter, der dafür die Locale umschaltet. Der Import übernimmt Sprache und Übersetzungsgruppen, die Sprache vor den Kategorien (Polylang verwirft Terms anderer Sprache). Polylang filtert `get_posts`/`get_terms` auf eine Sprache, auch in Cron und CLI: Abfragen, die alles brauchen (Import-Lookups, `sync_all`, Uninstall), setzen `'lang' => ''`. In der Testseite ist Polylang mit de/en installiert; `seed-demo.php` legt dann zwei englische Veranstaltungen an.
- Noch offen: Theme-Templates, öffentliche Kategorie-Archive.
- **Status eines Termins** (`Domain\Occurrence`): `scheduled`, `cancelled` (Veranstalter hat abgesagt) und `withdrawn` (Markt findet statt, aber ohne uns; nur bei Art `market`). Je Termin über `overrides[key].status`; im Editor wählt man das im Termin-Kasten (Einzeltermine, auch vergangene) bzw. in „Nächste Termine“ (Termine einer Regel). Für die ganze Veranstaltung gibt es `details.status`; im Editor nur noch „abgesagt“, `withdrawn` wird dort nur angezeigt, wenn es aus 0.3.0 gesetzt ist. `OccurrenceSync::status()` entscheidet, was in der Index-Tabelle steht: abgesagt schlägt alles, `withdrawn` gilt nur für Märkte. `OccurrenceQuery` liefert `cancelled` und `withdrawn` als Booleans; Ausgabe mit Klasse `is-withdrawn` und Text „We are not taking part“. Strukturierte Daten bleiben bei `EventScheduled`, weil der Markt stattfindet.
- **Farbstreifen**: grau = vorbei, grün = kommt noch, rot = kommt noch, aber abgesagt oder ohne uns. Im Editor über `entryState()` in `model.js` (Klassen `is-past|is-upcoming|is-off`), in der Backend-Liste über `ListTable::row_class()` (`rmd-eo-is-*`).
- **Backend-Liste** (`Admin\ListTable`): Filter `rmd_eo_when` (`upcoming`, `past`, `off`, `undated`; IDs aus der Index-Tabelle, Reihenfolge nach Termin), `rmd_eo_kind`, `rmd_eo_cat`, `rmd_eo_loc`. Der Monatsfilter von WordPress (Erstelldatum) ist ausgeblendet.
- **Zugriff**: Capability `rmd_eo_manage_events` (Administrator immer, weitere Rollen über Einstellung `roles`); Einstellungen nur mit `manage_options`. Capabilities regeln, wer etwas darf; Module, ob es die Funktion gibt.
- Admin-Editor: React-App (`src/admin/event-editor`) unter dem Titel (`edit_form_after_title`), Zustand als JSON im hidden Feld `rmd_eo_data`; PHP validiert in `Admin\SaveHandler`. Die Wiederholungslogik existiert nur in PHP, die Vorschau kommt über `POST rmd-events-organizer/v1/preview` (schreibt nichts).
- Blocks: `src/blocks/*` (`rmd/events`, `rmd/market-dates`, `rmd/events-calendar`, `rmd/event-details`) mit `block.json` + `render.php`; Shortcodes spiegeln sie und nutzen dieselben Renderer (`includes/Render/`). Front-Assets liegen ungebaut in `assets/`.
- **Darstellungen**: Jeder Block hat drei Block-Stile (`styles` in `block.json`, Reiter „Stile“ der Block-Seitenleiste): Listen `default|cards|plain`, Kalender `default|tiles|plain`, Details `default|banner|plain`. Die Listen der erlaubten Werte stehen in `Domain\Settings::*_STYLES` (erster Eintrag = Standard). `Blocks::style()` liest den Stil aus `className` (`is-style-…`) und reicht ihn als `style` an den Renderer, der die Klasse `rmd-eo-<list|calendar|event>--<stil>` auf das Wurzelelement setzt; das CSS hängt nur an dieser Klasse, nie an `is-style-…`. Die Editor-Vorschau (`ServerSideRender` mit `skipBlockSupportAttributes`) verwirft `className`, deshalb schickt `previewAttributes()` den Stil im Attribut `previewStyle`. Shortcodes kennen `style`, die Einzelseite nimmt `display.single_style`. `plain` ist das Grundlayout ohne Dekoration (Basis für eigene Theme-Stylesheets), die anderen Stile bauen in `front.css` darauf auf. Die Akzentfarbe (`display.accent`) kommt als Inline-Style `.rmd-eo{--rmd-eo-accent…}`; die Variablen-Defaults stehen in `:where()`, damit jede Theme-Regel gewinnt. `--rmd-eo-accent` ist in den gestalteten Stilen bewusst nicht `currentcolor` (löst sich auf Flächen mit heller Schrift zur Schriftfarbe auf).
- Cache-Sicherheit: Listen tragen `data-end`, `assets/js/front.js` blendet Abgelaufenes aus; Kalender blättert über `GET rmd-events-organizer/v1/calendar` und fällt ohne JS auf Links (`?eo_month=`, `?eo_day=`) zurück.
- `Admin\HelpPage` ist die Nutzer-Doku im Backend; bei neuen Feldern, Attributen oder Blöcken dort **und** in README/PO nachziehen.

## Code-Regeln

- PHP 8.1+, WP 6.8+. WordPress-Coding-Standards (`phpcs.xml.dist`), Methoden snake_case, Präfix `rmd_eo_` / `RMD_EO_` / Namespace `RMD\EventsOrganizer`, CSS `rmd-eo-`, Textdomain `rmd-events-organizer`.
- Quellstrings Englisch, Übersetzung in `languages/rmd-events-organizer-de_DE.po` von Hand nachziehen (`npm run i18n` erzeugt POT/MO/JSON; braucht WP-CLI, läuft im Workflow). Die Übersetzung siezt; `de_DE_formal` erzeugt `make-i18n.sh` daraus.
- Sicherheit: jede Schreiboperation prüft Nonce + Capability; Ausgabe escapen; REST schreibt nichts; keine externen Aufrufe außer Update-Check.
- Version an vier Stellen: Plugin-Header, `RMD_EO_VERSION`, `package.json`, `readme.txt` (Stable tag) und `src/blocks/*/block.json`. `bash bin/check-version.sh` prüft das.
- Schemaänderungen: `Schema::VERSION` erhöhen (dbDelta läuft über `Upgrade::run`); Datenmigrationen als Schritt in `Upgrade`.
- `RMD_EO_FAKE_NOW` (nur mit `WP_DEBUG`) in `wp-config.php` erlaubt Zeitreisen zum Testen.

## Build und Prüfung

```powershell
npm run build          # Blocks + Admin-Editor nach build/
npm run lint           # JS + SCSS
npm run test:js        # Jest (Editor-Modell)
composer phpcs         # PHPCS
composer test          # PHPUnit (Domain)
npm run zip            # dist/rmd-events-organizer.zip (Git Bash: rsync, zip, composer nötig)
```

Composer liegt unter `C:\xampp\php\composer.bat`.

Testen in WordPress: nie in Kundenseiten. Die Testseite ist `C:
mpp\htdocs	estwordpress` (`http://localhost/testwordpress/`); `bin/link-local.ps1 -WordPressPath "C:
mpp\htdocs	estwordpress"` bindet das Repo per Junction ein (dort ist auch Events Manager installiert). Demo-Daten im Format von Events Manager 7.x legt `php tests/fixtures/em/seed-demo.php "C:/xampp/htdocs/testwordpress"` an (alles mit `[em-demo]` im Namen, wird bei jedem Lauf ersetzt); für echte Altbestände mit Datenbank-Klonen arbeiten.

## Git und Release

- Committen nur auf Anfrage, auf Feature-Branches; nie direkt auf `main`.
- Release: Versionen an allen Stellen erhöhen, `CHANGELOG.md` und `readme.txt` (Changelog) ergänzen, committen, Tag `vX.Y.Z` pushen. Der Workflow lintet, testet, baut Assets + Übersetzungen, erzeugt `rmd-events-organizer.zip` sowie `update.json` und legt ein **Draft-Release** an. Beide Assets müssen am Release bleiben (installierte Sites lesen `releases/latest/download/update.json`).
- Den vom Workflow angelegten Entwurf bearbeiten (Releases → Entwurf → Stift), nicht neu anlegen; erst nach Test des ZIPs veröffentlichen.
- Bei jedem Release Titel `vX.Y.Z – <Kernänderung>` und Release Notes (Englisch, Markdown in Codeblock) mit ausgeben; Grundlage `git log <letzter Tag>..HEAD`.
- Topics fürs Repo: `wordpress`, `wordpress-plugin`, `gutenberg-block`, `events`, `calendar`.
- Nach dem ersten veröffentlichten Release: Plugin in `rmd-wordpress.git/scripts/new-project/` (Script, Example-Config, lokale Config, README) aufnehmen und den Doku-Block `rmd-docs/blocks/plugins/rmd-events-organizer.md` anlegen.
